The hardware

Three parts, no soldering, and the board does the hard bit for you.

A HUB75 LED matrix is a dumb display. It has no framebuffer and no controller — you feed it one row at a time over a parallel bus and refresh the whole panel hundreds of times a second, forever, or it visibly flickers. On a general-purpose microcontroller that eats the CPU.

The MatrixPortal S3 is worth its $20 because the ESP32-S3 has a hardware parallel peripheral, and the board drives the panel through it with DMA instead of bit-banging. The refresh happens off-CPU, so your code gets the processor to itself. It also presses directly onto the panel's connector, which is why there is no wiring.

SpecValue
Panel64 × 32 pixels, 4 mm pitch, 255 × 127 × 15 mm
Readable atAcross a room. 4 mm is the coarse pitch — that is the point

Assembly, in order

1. peel the tape off the two threaded standoffs
2. panel's power harness  ->  spade lugs onto +5V and GND
3. 5V 4A supply           ->  same two standoffs
4. MatrixPortal           ->  press onto the 8x2 shrouded connector
5. power up — it ships with a demo, so you see it work before writing code

Meter the supply before you connect it. Wire markings on barrel supplies are not consistent, and reversed 4 A will destroy the panel. This is the only step that can cost you money.

Do not try to run the panel from the MatrixPortal's USB-C alone. Under-powering a HUB75 does not fail cleanly — you get flicker, colour corruption, and ESP32 brownout resets that look exactly like WiFi bugs. That is a miserable afternoon for the sake of a $15 supply.

The board runs unattended off flash once flashed. It needs power and 2.4 GHz WiFi and nothing else — no host, no serial. Check your SSID actually carries a 2.4 GHz band first; the ESP32-S3 has no 5 GHz radio, and a band-steered network can look like it works right up until it doesn't.

Reading the camera

The whole Mac side is one CoreMediaIO property, polled once a second.

macOS exposes every camera — built-in, USB, Continuity, and virtual devices like OBS — as a CoreMediaIO object. Each carries a boolean, kCMIODevicePropertyDeviceIsRunningSomewhere, that is true whenever any process is pulling frames from it. Enumerate the devices, read the flag, OR the results.

import CoreMediaIO

let systemObject = CMIOObjectID(kCMIOObjectSystemObject)

func address(_ selector: Int) -> CMIOObjectPropertyAddress {
    CMIOObjectPropertyAddress(
        mSelector: CMIOObjectPropertySelector(selector),
        mScope: CMIOObjectPropertyScope(kCMIOObjectPropertyScopeGlobal),
        mElement: CMIOObjectPropertyElement(kCMIOObjectPropertyElementMain))
}

func cameraDevices() -> [CMIOObjectID] {
    var addr = address(kCMIOHardwarePropertyDevices)
    var size: UInt32 = 0
    guard CMIOObjectGetPropertyDataSize(systemObject, &addr, 0, nil, &size) == 0,
          size > 0 else { return [] }
    var ids = [CMIOObjectID](
        repeating: 0, count: Int(size) / MemoryLayout<CMIOObjectID>.size)
    var used: UInt32 = 0
    guard CMIOObjectGetPropertyData(
        systemObject, &addr, 0, nil, size, &used, &ids) == 0 else { return [] }
    return ids
}

func isStreaming(_ device: CMIOObjectID) -> Bool {
    var addr = address(kCMIODevicePropertyDeviceIsRunningSomewhere)
    var value: UInt32 = 0
    var used: UInt32 = 0
    guard CMIOObjectGetPropertyData(device, &addr, 0, nil,
        UInt32(MemoryLayout<UInt32>.size), &used, &value) == 0 else { return false }
    return value != 0
}

That is the load-bearing part. Names come from kCMIOObjectPropertyName on the same objects, which is how you exclude a virtual camera — an OBS Virtual Camera left running would otherwise pin the sign to On camera all day.

Why this beats every other approach

  • No permission prompt. You read device metadata and never open an AVCaptureSession, so TCC is not involved. Nothing appears under Privacy & Security, and the daemon works from launchd on first launch.
  • No polling cost worth measuring. Two property reads per device, once a second.
  • It is actually correct, unlike lsof grepping or log scraping. See traps 1 and 2.

Measured latency on my machine: about 1.6 s from opening Photo Booth to the panel turning red, and 0.6 s to clear. Most of that is the app starting up, not the poll.

The daemon publishes on every state change plus a heartbeat, which is what lets the sign distinguish "camera is off" from "the Mac has gone away". Without the heartbeat there is no way to tell, and the sign eventually lies.

Eight traps

The parts are easy. These are what actually cost me time — skip straight here if you build one.

1. lsof lies about who is using the camera

lsof | grep VDC → Safari, Brave, Slack, Claude, Granola, Spark

Every popular snippet greps lsof for the CoreMediaIO plugin. On my machine that named six apps, none of which were using the camera — they merely had the plugin memory-mapped. Poll kCMIODevicePropertyDeviceIsRunningSomewhere instead. It is accurate, and it needs no camera permission at all, because you never open a stream.

2. The log-scraping recipes are dead

com.apple.cmio … client <private> resolvedIdentity: <private>

Older projects parse log stream for camera events. On current macOS, AVFCapture messages returned nothing over 48 hours, and every identifying field in the cmio subsystem is redacted. Un-redacting needs a configuration profile. There is also no supported API for which app holds the camera — treat any project claiming per-app attribution with suspicion.

3. Cloudflare WARP swallows your LAN

route -n get 192.168.x.x → interface: utun0

Mac and board sat on the same subnet and could not reach each other in either direction. WARP runs in Exclude mode with no RFC1918 range among its entries, so local traffic routes into the tunnel and dies. It is Always-On and Switch-Locked, so you cannot just turn it off. Either file an IT request to exclude 192.168.0.0/16, or relay through something public. The giveaway is a 100.64.0.0/10 source address in a failed curl.

4. CircuitPython floats are single precision

clock read 6:29 while the Mac read 6:20

A Unix epoch is about 1.8×109, which needs ten significant digits. float32 gives roughly seven, so representable values up there are ~128 seconds apart. Storing the epoch in a float put the clock nine minutes fast. Keep both time anchors as integers and take the elapsed term from time.monotonic_ns().

5. Google OAuth has two settings that decide everything

Testing → refresh tokens expire after 7 days

An Internal consent screen only authorizes accounts inside its own Workspace, so it cannot cover several domains. And an External app left in Testing issues refresh tokens that die weekly — fatal for a daemon, and it fails silently a week after you stop paying attention. External, published to production, unverified is the combination that works. Also: an API key cannot read a private calendar at all, only public data.

6. Adafruit IO does not auto-create feeds

POST /feeds/onair/data → 404 not found

Posting data to a feed that does not exist returns 404 rather than creating it. Create the feed first, through the dashboard or a POST to /feeds.

7. Ten characters, and not one more

"until 11:30" = 11 chars = 66px on a 64px panel

terminalio.FONT is 6 px wide, so a 64 px panel holds exactly ten characters. Write the copy to that budget before you fall in love with it: until 11:30 overflowed by one and clipped a pixel off each edge, while ends 11:30 fits exactly. Text bigger than scale=1 means hand-building a glyph set, which is real work for a handful of characters.

8. Equal red and green is not yellow

0x555500 → reads plainly green

Green LEDs are far more luminous per unit drive than red, so driving both channels equally does not produce yellow — it produces green with a faint warm cast. A convincing orange needed red at level 5 against green at 3. Do not reason about these panels in sRGB; put candidates side by side on the hardware and pick by eye.

If you build one

Two pieces of code: a Swift daemon on the Mac and a CircuitPython code.py on the board. Neither is long. The daemon runs as a launchd agent with KeepAlive; the board runs unattended off flash and needs nothing but power and 2.4 GHz WiFi — the ESP32-S3 has no 5 GHz radio, so check your SSID actually carries a 2.4 GHz band before you order.

Build in a staleness fallback from the start. If the Mac sleeps mid-meeting and the sign has no timeout, it stays lit as busy indefinitely, which is worse than having no sign. Mine falls back to the clock after 90 seconds of silence.
